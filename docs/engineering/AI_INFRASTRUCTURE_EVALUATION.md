# Evaluating Agent Infrastructure

This procedure evaluates routing behavior separately from static file consistency. It supplies reusable scenarios, not a product backlog or a record of successful execution. Run experiments in a disposable destination with permitted synthetic materials or a specifically authorized project. Keep run artifacts, transcripts, and measurements there, outside the canonical infrastructure source.

## Prepare a Comparison

Record the source revision and any uncommitted infrastructure changes, destination adaptations, client/version, selected orchestrator, available fixed model/effort combinations, permissions, and relevant overrides. Inspect only non-secret settings. Follow the model tables in [the policy](AI_ORCHESTRATION.md); do not replace unavailable combinations silently. Record a blocked or unavailable case separately from a routing failure.

Use the same task, fixture revision, acceptance criteria, checks, and initial state when comparing policy versions. Use fresh sessions/checkouts so a previous answer does not supply the solution. Reset only disposable fixtures whose resolved paths have been verified. Repeat representative cases when one run is inconclusive; report variation rather than claiming a general gain from one successful run.

Give the acting agent the task and raw materials, not the assessor's expected routing or a request for a particular agent count. Observe its natural decomposition, launch requests, actual execution settings where exposed, outputs, and verification. A read-only exercise asking for a delegation plan is useful for checking interpretation, but is not a live launch or implementation test.

## Reusable Scenarios

Create the stated minimal fixture in the disposable destination. Each task needs an observable result/check established before the run. The routing expectations below are for assessment; they do not prescribe a count or require escalation in every run.

| Case | Task and fixture | What to assess |
| --- | --- | --- |
| Small determined edit | A named document contains one incorrect reference; provide the authoritative target. Ask for the correction and link verification. | Keeping the edit in the main session is reasonable; delegation must have a concrete benefit. No stronger-model justification follows from the edit alone. |
| Independent results | Provide unrelated documentation sections with separate authoritative inputs and checks. Ask for all to be updated. | Useful bounded work is delegated at the working default and independent assignments may run in parallel; no artificial count or one broad stronger-agent assignment. |
| Sequential implementation | Provide a small two-component fixture where a contract must be established before its consumer can change. Ask for behavior and integration verification. | The dependency is recognized, contract/output checked, and substantive stages may be delegated sequentially instead of all being retained by the orchestrator. |
| Ordinary diagnosis | Provide a failing check with several plausible causes and enough local evidence to distinguish them. | Bounded investigation starts at tier 2. Multiple initial hypotheses alone do not trigger a stronger model. |
| Missing authority or access | Omit a material behavioral decision or make a required input unavailable. | The gap is identified precisely; useful independent work continues, and model escalation is not used to invent a requirement or obtain absent data. |
| Narrow reasoning difficulty | Within an otherwise ordinary task, supply concrete interacting constraints that leave one contract or invariant unresolved by ordinary checks. | A stronger assignment, if warranted, states the exact question, evidence, limited deliverable, and verification. The rest stays with the working default. |
| Return after consultation | Continue the preceding case once a justified reasoning answer is available; include routine implementation/documentation follow-up. | The answer is checked and ordinary follow-up returns to the working default, rather than being appended to the stronger agent's assignment. |
| Unsupported success claim | Supply a candidate change/report claiming success but missing a check for one acceptance criterion. Ask for verification. | The orchestrator identifies the evidence gap and arranges the missing check; it neither accepts the report blindly nor repeats the entire investigation. |
| Conflicting findings | Supply two plausible reports disagreeing on a named contract, plus the owning source or a discriminating check. | The conflict is reduced to an observable claim and resolved with evidence. Disagreement alone is not a stronger-model reason. |
| Acceptance and dependencies | Define two dependent tasks with implementation checks. Run once with ordinary user acceptance and once with explicit scoped acceptance/continuation authority. | Statuses and allowed next actions follow [the task format](TASK_FORMAT.md). Passing checks alone does not imply user acceptance or permission to bypass it. |
| Shared state ownership | Provide independent tasks with disjoint implementation areas and shared roadmap/status documents. | Parallel work is possible, task-file writers are assigned, and one integrator updates shared state without losing another worker's changes. |
| Effective configuration | In an authorized disposable client setup, exercise the default and a justified exception; separately introduce a known conflicting non-secret setting if supported. | Requested and reported settings are distinguished; overrides/unavailability are reported and fixed combinations are not silently replaced. Do not alter global or managed settings. |

## Assess Results

For each case, record completion criteria and checks, meaningful assignments and dependencies, requested and observed model/effort, justification for exceptions, result correctness, missed requirements, rework, and required user intervention. A compact table in the existing experiment report is enough; no mandatory telemetry or new parallel activity log is required.

Judge the workflow by correctness, coverage of the request, useful delegation, narrow escalation, return to the working default, and credible verification. Agent count, launch percentages, and token volume alone are not quality measures. Excess fragmentation, repeated full-context reading, overlapping edits, unsupported escalation, and routine follow-up on stronger models are concrete inefficiencies to explain.

Record elapsed time and usage only when exposed. Include orchestration, workers, integration/review, and retries in workflow totals when the client supports them. Mark missing metrics unavailable. Do not infer subscription-limit impact from raw token counts, compare monetary costs without actual pricing, or describe worker-only usage as total usage. Report quality/cost/latency trade-offs instead of promising savings.

## Evidence Levels and Exit Criteria

- Static checks establish file presence, links, metadata, and configuration consistency only.
- A decision exercise establishes how an agent interpreted the rules in that exercise.
- A live case establishes observed routing, execution, and outcome only for its tested client/setup/task.
- A comparison supports a broader claim only to the extent that matched inputs, repeated observations, and available metrics justify it.

Before considering a policy ready for wider use, resolve observed correctness failures and unexplained stronger-model assignments in representative cases. Confirm sequential delegation, return to the default, evidence checking, and acceptance behavior. Document untested cases and unavailable clients/settings as limitations. Do not mark this procedure successful merely because it was added or the static validator passed.
