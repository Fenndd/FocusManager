# T054 — Fix Windows path compatibility after review

## Goal

Resolve the two verified Windows compatibility defects from the uncommitted-change review and retain evidence that the T001 refactor preserves the affected existing behavior.

## Sources

- [Review and exact cases](../docs/reviews/2026-11-18-uncommitted.md), [retained probes](../docs/reviews/evidence/2026-11-18/README.md).
- [T001](T001-make-core-path-rules-os-independent.md), [T012 boundary](T012-align-core-rules-with-spec.md).
- [Application requirements](../docs/spec/apps.md), [folder requirements](../docs/spec/folders.md), [ADR-0005](../docs/architecture/decisions/0005-native-stack-per-platform.md), [architecture](../docs/architecture/README.md).
- Owner instruction on 2026-11-18: record bounded follow-up work; all Linux development is halted pending explicit owner resumption.

## Scope

In scope: restore compatibility for the drive-root UI/storage round trip, rooted-relative and trailing-dot cases actually reproduced on Windows/.NET 8; correct colon handling in filename extraction; add focused regression tests and minimal JSON shared examples. Keep shared code free of OS APIs/implicit host state; any necessary Windows context belongs at the platform boundary. Inspect the actual normalization behavior before selecting the fix. Update the owning specification before any behavior change; record material decisions separately rather than inventing a new product rule.

This is remediation of unaccepted T001 work. It needs no accepted new feature output, so `depends_on: []` is intentional and does not accept T001/T002. Do not expand into T012's full-path-only, empty-list, domain/subdomain changes, T022's complete loader/suite, storage/service/IPC architecture, or arbitrary new path semantics. Do not provision, run, research, or develop Linux; preserve existing sources. Windows-host Shared checks are allowed. Coordinate edits to tests with T055 and the main agent.

## Acceptance Criteria

Any Windows adapter needed for the demonstrated compatibility must stay in the Windows platform project
and its tests, with explicit wiring. Do not rewrite the accepted APP-002/decision I1 requirements to
legitimize the legacy filename fallback; preserving this refactor's baseline is separate from T012's
already-approved behavior change. Specification edits here describe verified implementation state/clarifications.

1. Focused Windows tests reproduce the review's four differences before the fix and pass afterward against explicit expected compatibility results; the unchanged child-folder control remains allowed. Document the Windows drive/context used for relative-path comparison.
2. A Windows UI-selected root that is saved as `D:` still permits the corresponding root `D:\` after persistence/reload; cover the actual normalization boundary, without requiring a physical D: drive where a synthetic test suffices.
3. `C:\Apps\evil.exe:Code.exe` does not become allowed solely because `C:\Apps\Code.exe` is allowed; retained filename fallback behavior stays within T001's scope.
4. Shared code retains explicit path semantics and no OS calls/implicit current-directory dependency. Windows/Unix-style existing test coverage remains passing on Windows. A required unresolved product interpretation is surfaced before affected implementation.
5. Minimal JSON examples in `test-vectors/` encode the changed Windows matching inputs and expected results with identifiable path style. They are inspected against regression tests; this task does not require a new complete loader.
6. Actual checks and limitations are recorded, task enters `review`, and T001/T002 are not marked accepted. Linux AC1 remains explicitly deferred under owner hold.

Fix chosen after inspecting the real behavior:
- UI boundary: `FoldersWhitelistPage.NormalizeFolderPath` runs `Path.GetFullPath` and trims trailing separators, so a selected `D:\` is persisted as `D:`. A test mirrors that function (the WinUI project cannot be referenced from tests); the UI file itself is unchanged. The pre-T001 evaluator then resolved `D:` through `Path.GetFullPath` to the per-drive current directory (the root `D:\` in the recorded run) and `\Study` to `<current drive>:\Study`.
- Host-dependent resolution is a Windows adapter: new `src/Windows/FocusManager.Platform.Windows/WindowsHostPathRules.cs` wraps `PathRules.Windows`, resolves values that are not fully qualified, or contain `~`, through `Path.GetFullPath` (replaceable delegate for synthetic hosts), and keeps the raw value if resolution throws. It is registered explicitly in `src/Windows/FocusManager.Agent/Program.cs` (`AddWindowsPathRules()`: `IPathRules` = `new WindowsHostPathRules()`, `RuleEvaluator` built from it; see the review follow-up below). `D:Study` and plain relative names keep their HEAD behavior because the adapter supplies it; no new product rule was invented and no owner question was needed.
- Pure lexical fixes in `src/Shared/FocusManager.Core/Rules/PathRules.cs` (`PathRules.Windows`): Win32 trailing-dot/space trimming (one trailing dot of inner segments; all dots and spaces of the final component when the path does not end in a separator; UNC server/share protected), and `GetFileName` treats a colon as a boundary only as the drive prefix, so `C:\Apps\evil.exe:Code.exe` has file name `evil.exe:Code.exe`. `PathRules.Unix` is unchanged. Core has no `System.IO.Path`/`Environment`/current-directory use (grep finds only a doc comment mentioning `Path.GetFullPath`); `RuleEvaluator` still has no `Path.GetFullPath`/`Path.DirectorySeparatorChar` and takes `IPathRules` explicitly (T001 AC3-5 properties kept).
- Specification (clarification of implementation state only, no change of requirement meaning): `docs/spec/folders.md` (FLD-002) and `docs/spec/apps.md` (APP-002).
- Tests: `tests/Shared/FocusManager.Core.Tests/WindowsCompatibilityRegressionTests.cs` and `WindowsPathCompatVectorTests.cs`; `tests/Windows/FocusManager.Platform.Windows.Tests/WindowsHostPathRulesTests.cs` (includes a generated parity test over thousands of fully qualified paths per prefix against the pre-T001 `Path.GetFullPath` normalization) and `WindowsPathCompatVectorTests.cs`. Both test csproj files copy `test-vectors/**/*.json` next to the assembly. Expected values come from HEAD evaluator behavior (review evidence), not from the new code.
- Vectors: `test-vectors/README.md` (fields `pathStyle`, `kind`, `allowed`, `input`, `expected`, optional `hostContext`) and `test-vectors/windows-path-compat.json` (8 cases: the four review differences, the child-folder control, an application full-path control, and `D:` with and without subfolders). Both test projects read and verify them with a tiny inline reader (not T022's loader); cases without `hostContext` also run through pure `PathRules.Windows` in Core.

Windows context used for relative-path comparison: current drive is the drive of the test process working directory (C:), and drive D: has no per-drive current directory other than its root, so `Path.GetFullPath("D:")` is `D:\` (asserted as a premise in the test). Synthetic-host tests use current drive C: with explicit per-drive directories (vector `hostContext`).

Review follow-up (2026-11-19, tier-2 executor): the independent review verdict was accept-with-fixes (eight findings, none major). Each was checked against the real code and .NET 8.0.25 (`dotnet --list-runtimes` shows 8.0.25 among others; probes ran in a scratch `net8.0` console project referencing Core, not on a newer runtime). All eight were real; none was rejected. The lifecycle status is not changed here (the main agent owns it); the earlier note that the findings were not yet applied is superseded.
- Device and verbatim roots (findings 1, 3): `PathRules.Windows` now treats a `\\.\` prefix (and `//./`, `//?/`, which .NET normalizes) as a four-character root, so the `.`/`?` is never dropped or counted as a UNC server, `\\.\C:\Study\..\..\Windows` becomes `\\.\Windows` as in .NET, and `\\.` alone is a device root. A path with the literal `\\?\` or `\??\` prefix is not normalized (Win32 and .NET leave it as written; only trailing separators were trimmed before): this is parity with the pre-T001 behavior, not a divergence. Consequence kept from HEAD: a stored verbatim folder with subfolders compares literally, so `\\?\C:\Study\..\Other` is a child of `\\?\C:\Study`; the folder picker does not produce such values.
- `GetFileName` (finding 2): rewritten to follow `Path.GetFileName` (`i < root ? root : i + 1`) with a lexical root length (drive, `\`, UNC server/share, `\\?\UNC\server\share`, device prefix plus first segment), so no component inside the root is returned. `\\server\Code.exe`, `\\.\Code.exe`, `\\?\Code.exe`, `\\?\C:` no longer match the file-name fallback (HEAD: deny). The `C:\Apps\evil.exe:Code.exe` behavior is unchanged. Unix is unchanged.
- 8.3 short names (finding 4): `WindowsHostPathRules` also calls the host resolver when the value contains `~` (the expansion needs the file system); `~` was added to the adapter parity tokens.
- Parity generator (finding 5): prefixes now include `\\.\`, `\\.\C:\`, `//./C:/`, `//?/C:/`, `\\?\C:\`, `\??\C:\` besides `C:\`, `c:/`, `\\srv\share\`; token `:` added; the pure rules are checked without `~` and the adapter with `~`. Documented exclusion, asserted explicitly: for non-verbatim device prefixes the `~` run is skipped because .NET itself garbles a short-name expansion there (`\\.\C:\..\a~` becomes `\\.\\~`); `DevicePathWithShortNameCharacter_IsExcludedFromParity_ButStaysDeviceRooted` pins that the adapter neither throws nor loses the device root. Other known non-goals: `1:\x` style non-letter drive prefixes.
- Production composition (finding 6): the registration moved into `FocusManager.Agent.Composition.PathRulesRegistration.AddWindowsPathRules` (declared in `Program.cs`, which `Program.cs` calls; no new file or package). `tests/Windows/FocusManager.Agent.Tests/PathRulesCompositionTests.cs` resolves it from a real container (adapter type, `D:` round trip against the host's own `Path.GetFullPath("D:")`) and reads `Program.cs` to require the call and forbid the pure rules. Mutation check: registering the pure Windows rules made all three tests fail; reverted. Limit: the host is not started, so wiring is guarded by container resolution plus a source check.
- Spec nits (finding 7): blank line added in `docs/spec/folders.md` and `docs/spec/apps.md`; the apps.md note now says it describes the retained legacy file-name fallback (T012 removes it under I1) and not an APP-002 requirement; folders.md mentions device, verbatim and 8.3 handling.
- Vectors: four cases added to `test-vectors/windows-path-compat.json` (UNC server component, device root component, device `..` escape, device child control; all with no `hostContext`). Verbatim cases are kept in unit tests only, because they pin Win32 literal semantics that other platforms should not inherit.
